App Factory Autopilot 통합 설계서

1. 프로젝트 개요

프로젝트 이름은 App Factory Autopilot이다.

App Factory Autopilot은 아무것도 없는 빈 폴더에서 앱 기획을 시작하여, 요구사항 수집, 기술 결정, 로드맵 작성, 공식 문서 조사, 프로젝트 생성, 전체 기능 구현, 빌드와 테스트, 에뮬레이터 검증, 사용자 가치 분석, 2차 로드맵 작성, 품질 정밀점검, 라이브러리 버전 관리, 라이선스 검사, 최종 완료 검증까지 자동화하는 앱 개발 오케스트레이션 시스템이다.

Claude Code와 Codex에서 모두 사용할 수 있어야 하며, 특정 AI 도구의 내부 기능에 강하게 종속되지 않는 구조로 제작한다.

사용자에게 노출되는 핵심 명령은 다음 세 가지로 단순화한다.

factory plan "만들고자 하는 앱에 대한 설명"

factory go

factory review

Claude Code에서는 다음과 같이 호출한다.

/factory plan "만들고자 하는 앱에 대한 설명"

/factory go

/factory review

Codex에서는 다음과 같이 호출한다.

$factory plan "만들고자 하는 앱에 대한 설명"

$factory go

$factory review

공통 CLI에서는 다음과 같이 호출한다.

factory plan "만들고자 하는 앱에 대한 설명"

factory go

factory review

Claude Code와 Codex의 명령 표현은 다르지만 내부적으로는 동일한 Factory 워크플로를 실행한다.

2. 핵심 설계 원칙

App Factory Autopilot은 하나의 거대한 프롬프트가 모든 작업을 수행하는 방식으로 만들지 않는다.

전체 시스템은 다음 요소로 분리한다.

결정론적 오케스트레이터

공통 워크플로 상태 머신

전문 Agent

재사용 가능한 Skill

공통 MCP 서버

Claude Code 어댑터

Codex 어댑터

빌드, 테스트, 라이선스, 버전, 실행 검증 게이트

상태 및 증거 저장소

가장 중요한 원칙은 구현과 완료 판정을 분리하는 것이다.

코드를 구현한 Agent는 자신이 구현한 작업을 완료 상태로 직접 변경할 수 없다.

구현 Agent는 IMPLEMENTED 상태까지만 요청할 수 있다.

별도의 Completion Verifier Agent가 코드, 호출 경로, 테스트, 빌드 결과, 실행 결과를 독립적으로 검증한 뒤에만 VERIFIED 상태로 변경할 수 있다.

로드맵의 체크박스나 기존 완료 표시는 신뢰하지 않는다.

부분 구현, 호출되지 않는 코드, 비어 있는 UI, Mock 데이터, TODO, Placeholder, 실패 경로 누락, 테스트 없는 구현 등이 발견되면 완료 상태를 취소하고 다시 작업 대상으로 등록한다.

4. 사용자 명령 체계

4.1 factory plan

factory plan은 빈 폴더에서도 실행할 수 있다.

사용자가 만들고자 하는 앱을 한 문장 또는 여러 문장으로 설명하면, App Factory Autopilot이 필요한 정보를 분석하고 대화형 인터뷰를 시작한다.

factory plan은 코드를 구현하지 않는다.

factory plan의 목적은 사용자의 판단이 필요한 내용을 빠짐없이 확인하고, 1차 로드맵과 프로젝트 계획을 완성하는 것이다.

사용자가 답하지 못하거나 아직 결정하지 않은 항목은 임의로 꾸며내지 않는다.

확정되지 않은 항목은 명시적인 Placeholder로 기록한다.

예시는 다음과 같다.

${PLACEHOLDER_APPLICATION_ID}

${PLACEHOLDER_ADMOB_APP_ID}

${PLACEHOLDER_BANNER_AD_UNIT_ID}

${PLACEHOLDER_REMOVE_ADS_PRODUCT_ID}

${PLACEHOLDER_PRIVACY_POLICY_URL}

${PLACEHOLDER_KEYSTORE_PATH}

Placeholder는 단순한 문자열이 아니라 종류, 중요도, 해결 시점, 자동 진행 가능 여부를 함께 기록한다.

4.2 factory go

factory go는 factory plan 결과를 기반으로 전체 앱 제작 공정을 시작한다.

프로젝트가 없는 빈 폴더라면 프로젝트를 생성한다.

이미 프로젝트가 있다면 현재 상태를 분석하고 로드맵과 구현 상태를 동기화한다.

factory go는 다음 작업을 자동으로 수행한다.

프로젝트 초기화

기술 스택 구성

공식 문서 인덱싱

에뮬레이터 기능 검증

사용자 핵심가치 분석

경쟁 앱 및 커뮤니티 요구 조사

2차 로드맵 작성

2차 로드맵 구현

전체 품질 Agent와 Skill 순회

최종 완료 게이트 수행

사용자의 승인 없이 수행하면 위험한 작업은 자동으로 중단한다.

4.3 factory review

factory review는 구현이 완료되었다고 가정하지 않고 전체 프로젝트와 전체 공정을 처음부터 다시 감사한다.

factory review는 가능하면 구현에 참여하지 않은 다른 Agent 또는 다른 Provider가 수행한다.

Codex가 주요 구현을 담당했다면 Claude Code가 검증하도록 할 수 있다.

Claude Code가 주요 구현을 담당했다면 Codex가 검증하도록 할 수 있다.

factory review에서는 다음을 확인한다.

사용자가 기대한 핵심가치가 실제로 구현되었는지 여부

factory review는 문제를 발견하면 단순한 보고서만 생성하지 않는다.

자동 수정이 안전한 항목은 수정 작업으로 다시 등록할 수 있다.

위험하거나 제품 판단이 필요한 항목은 NEEDS_HUMAN_DECISION 상태로 남긴다.

5. factory plan 인터뷰 항목

factory plan은 한 번에 수십 개 질문을 나열하지 않는다.

관련 질문을 작은 묶음으로 나누어 진행한다.

이미 답변한 내용은 다시 묻지 않는다.

기술적으로 자동 결정 가능한 내용은 기본 추천값을 제시한다.

제품, 사업, 정책, 배포에 영향을 주는 항목은 사용자에게 명확하게 확인한다.

라이선스가 확인되지 않는 의존성은 자동 차단한다.

6. factory plan 산출물

factory plan 완료 시 다음 파일을 생성한다.

PROJECT_SPEC.md

ROADMAP.md

REQUIREMENTS_TRACEABILITY.md

TEST_MATRIX.md

DOCS_INDEX.md

USER_VALUE.md

DEPENDENCIES.md

DEPENDENCY_MIGRATIONS.md

LICENSE_POLICY.yaml

LICENSE_REVIEW.md

THIRD_PARTY_NOTICES.md

EMULATOR_SCENARIOS.md

QUALITY_FINDINGS.md

PLACEHOLDERS.md

APPROVALS.md

APP_FACTORY.yaml은 프로젝트 전체 설정의 기준 파일이다.

ROADMAP.md는 1차 구현 로드맵을 포함한다.

각 로드맵 항목에는 고유 ID를 부여한다.

각 항목에는 요구사항, 구현 범위, 완료 조건, 테스트 조건, 실행 검증 조건, 의존성, 우선순위, 위험도가 포함되어야 한다.

단순한 체크리스트만 작성하지 않는다.

7. 로드맵 상태 정의

로드맵 항목은 다음 상태 중 하나를 가진다.

NOT_STARTED

아직 구현을 시작하지 않은 상태다.

IN_PROGRESS

현재 구현 중인 상태다.

PARTIAL

일부만 구현되었거나 핵심 경로가 빠진 상태다.

IMPLEMENTED

구현 Agent가 구현을 완료했다고 제출한 상태다.

VERIFIED

Completion Verifier가 독립 검증을 통과시킨 상태다.

BLOCKED

외부 정보, 사용자 결정, 기술 문제 또는 승인 대기 때문에 진행할 수 없는 상태다.

NEEDS_HUMAN_DECISION

자동 판단으로 진행하면 위험한 상태다.

완료로 인정되는 상태는 VERIFIED뿐이다.

8. 주요 Agent 구성

8.1 Factory Orchestrator

전체 공정을 제어한다.

직접 코드를 대규모로 수정하지 않는다.

현재 상태를 읽는다.

다음 단계를 선택한다.

전문 Agent를 호출한다.

결과 형식을 검증한다.

실패 횟수를 기록한다.

재시도 여부를 결정한다.

작업 예산을 관리한다.

승인이 필요한 작업을 차단한다.

중단 후 재개를 관리한다.

8.2 Project Explorer

현재 폴더와 프로젝트 상태를 분석한다.

빈 폴더인지 확인한다.

기존 Android 프로젝트인지 확인한다.

모듈 구조를 분석한다.

Gradle 설정을 분석한다.

기존 라이브러리를 조사한다.

현재 구현 상태를 요약한다.

8.3 Roadmap Architect

사용자 인터뷰와 앱 설명을 기반으로 1차 로드맵을 작성한다.

기능 요구사항과 비기능 요구사항을 구분한다.

작업 의존성을 정리한다.

테스트 가능한 완료 조건을 작성한다.

Placeholder를 명확하게 기록한다.

8.4 Roadmap Auditor

로드맵의 누락과 모순을 검사한다.

완료 조건이 불명확한 항목을 찾는다.

테스트할 수 없는 요구사항을 찾는다.

구현 순서 오류를 찾는다.

광고, 결제, 개인정보, 접근성, 보안, 라이선스, 버전 관리 누락을 찾는다.

8.5 Official Docs Indexer

프로젝트에서 사용 중이거나 사용할 라이브러리를 자동 발견한다.

Mobile Docs MCP 또는 공식 문서 검색 수단을 사용한다.

공식 문서와 공식 릴리스 정보를 우선한다.

DOCS_INDEX.md를 갱신한다.

Deprecated API와 마이그레이션 요구사항을 기록한다.

공식 문서가 확인되지 않으면 임의로 결론을 내리지 않는다.

8.6 Dependency Version Manager

신규 라이브러리와 기존 라이브러리의 버전을 관리한다.

가장 숫자가 큰 버전을 선택하지 않는다.

최신 안정화 버전인지 공식 문서에서 확인한다.

현재 Kotlin, AGP, Gradle, JDK, Compile SDK, Target SDK, Min SDK와의 호환성을 확인한다.

Compose BOM과 AndroidX 버전 정렬을 확인한다.

Alpha, Beta, RC, Preview, Canary, Nightly, Snapshot 버전은 사용자 승인 없이 사용하지 않는다.

Version Catalog에 버전을 중앙 관리한다.

하드코딩된 버전을 탐지한다.

동적 버전과 플러스 버전을 금지한다.

필요한 마이그레이션 작업을 DEPENDENCY_MIGRATIONS.md에 기록한다.

8.7 License Compliance Auditor

직접 의존성과 전이 의존성의 라이선스를 검사한다.

SPDX 식별자를 기준으로 라이선스명을 정규화한다.

라이선스가 없는 라이브러리, 불명확한 라이브러리, 커스텀 라이선스는 자동 승인하지 않는다.

폰트, 이미지, 아이콘, 음원, 샘플 데이터, 복사한 소스, 로컬 AAR, JAR, SO 파일도 검사 대상으로 포함한다.

GPL과 AGPL 계열은 상업용 비공개 소스 앱의 기본 정책에서 차단한다.

LGPL, MPL, EPL, CDDL과 예외 조항이 있는 라이선스는 수동 검토 대상으로 분류한다.

법적 판단이 필요한 경우 NEEDS_LEGAL_OR_OWNER_APPROVAL 상태로 중단한다.

라이선스 감사 결과를 LICENSE_REVIEW.md에 기록한다.

Third Party Notices와 앱 내부 오픈소스 고지 데이터를 생성한다.

8.8 Implementation Worker

승인된 로드맵 항목을 구현한다.

한 번에 하나의 작업 또는 작은 작업 묶음만 수행한다.

코드와 테스트를 함께 작성한다.

변경 파일을 보고한다.

빌드 결과를 보고한다.

구현한 작업을 VERIFIED로 변경하지 않는다.

새 라이브러리가 필요하면 Dependency Request를 생성한다.

8.9 Completion Verifier

구현 Agent와 독립적으로 검증한다.

로드맵의 완료 표시를 신뢰하지 않는다.

실제 코드가 있는지 확인한다.

코드가 호출되는지 확인한다.

UI와 실제 동작이 연결되어 있는지 확인한다.

성공 경로와 실패 경로가 구현되었는지 확인한다.

설정값이 실제 기능에 반영되는지 확인한다.

Mock, TODO, Placeholder, 빈 함수가 남아 있는지 확인한다.

테스트가 실제 요구사항을 검증하는지 확인한다.

빌드와 실행 증거를 확인한다.

필요한 경우 에뮬레이터 검증을 요구한다.

검증을 통과한 항목만 VERIFIED 상태로 변경한다.

8.10 User Value Researcher

1차 로드맵 완료 후 작동한다.

현재 앱의 핵심가치가 실제로 구현되었는지 평가한다.

경쟁 앱의 기능과 사용자 리뷰를 조사한다.

커뮤니티에서 반복되는 요구사항과 불만을 조사한다.

기능을 단순 복사하지 않는다.

사용자 빈도, 문제 심각도, 핵심가치 적합성, 구현 비용, 유지보수 비용, 경쟁우위, 정책 위험, 수익화 영향을 기준으로 평가한다.

2차 로드맵 후보를 생성한다.

8.11 Quality Sweeper

설치된 관련 Agent와 Skill을 런타임에 발견한다.

Agent와 Skill 이름을 하드코딩하지 않는다.

한 번에 하나의 품질 점검만 수행한다.

각 점검 결과를 기록한다.

코드가 변경되면 빌드와 테스트를 다시 수행한다.

모든 스킬을 한 바퀴 순회한 뒤 새로운 중요 오류가 발견되면 다시 순회할 수 있다.

무한 순환을 막기 위해 최대 반복 횟수를 둔다.

8.12 Emulator QA

에뮬레이터 상태를 확인한다.

APK를 설치한다.

앱 데이터를 초기화한다.

앱을 실행한다.

핵심 시나리오를 수행한다.

Logcat을 수집한다.

크래시와 ANR을 확인한다.

스크린샷을 저장한다.

필요한 경우 화면 녹화를 저장한다.

테스트 결과를 Evidence Store에 등록한다.

8.13 Final Gate Reviewer

최종 상태를 콜드 컨텍스트에서 감사한다.

구현 Agent의 대화 기록을 신뢰하지 않는다.

코드, 로드맵, 테스트, 빌드 결과, 실행 증거만 검토한다.

완료 조건을 통과하지 못하면 프로젝트를 완료 처리하지 않는다.

9. 라이브러리 추가 승인 절차

Implementation Worker가 라이브러리가 필요하다고 판단하면 직접 추가하지 않는다.

먼저 Dependency Request를 생성한다.

Dependency Version Manager가 공식 문서와 공식 릴리스에서 최신 안정화 버전을 확인한다.

현재 프로젝트와의 호환성을 확인한다.

License Compliance Auditor가 직접 및 전이 의존성 라이선스를 확인한다.

보안 및 공급망 검사를 수행한다.

모든 검사를 통과한 뒤에만 Version Catalog에 추가한다.

단위 테스트

17. Claude Code와 Codex 교차 검증

두 Provider를 함께 사용할 수 있다.

예시는 다음과 같다.

Primary Provider는 Codex

Verification Provider는 Claude Code

또는 반대로 설정한다.

구현과 검증을 다른 Provider가 수행하면 동일한 추론 편향과 완료 오판을 줄일 수 있다.

동일 작업 트리에서 두 Provider가 동시에 코드를 수정하지 못하게 한다.

쓰기 Agent는 한 번에 하나만 실행한다.

읽기 전용 감사 Agent는 병렬 실행할 수 있다.

병렬 쓰기가 필요하면 Git Worktree를 분리한다.

검증 Provider는 구현 대화 기록이 아니라 코드, 로드맵, 테스트, 증거만 확인한다.

28. 최종 사용자 경험

사용자는 빈 폴더를 연다.

다음 명령을 실행한다.

factory plan "SSH, SFTP, SCP를 지원하고 비밀번호와 키 인증을 관리하는 Android 터미널 앱"

App Factory Autopilot은 앱 이름, 패키지명, 핵심 기능, 저장 방식, 보안, 광고, 인앱결제, 리뷰, 업데이트, 디자인, 다국어, 서명, 라이선스 정책 등을 순차적으로 질문한다.

결정되지 않은 값은 Placeholder로 남긴다.

인터뷰가 끝나면 1차 로드맵과 프로젝트 설정을 생성한다.

사용자는 내용을 확인한 뒤 다음 명령을 실행한다.

factory go

App Factory Autopilot은 프로젝트 생성, 공식 문서 확인, 최신 안정화 라이브러리 선정, 라이선스 검사, 전체 구현, 테스트, 빌드, 에뮬레이터 검증, 사용자 가치 분석, 2차 로드맵, 품질 스윕을 자동으로 진행한다.

완료 후 사용자는 다음 명령을 실행한다.

factory review

App Factory Autopilot은 구현 기록을 신뢰하지 않고 프로젝트 전체를 다시 검사한다.

부분 구현, 완료 오표기, 누락 기능, 테스트 공백, 버전 문제, 라이선스 문제, 정책 문제, 사용자 가치 부족을 발견하면 수정 대상으로 다시 등록한다.

모든 필수 검증을 통과한 경우에만 프로젝트를 완료 상태로 변경한다.

29. 최종 방향

App Factory Autopilot은 단순한 코드 생성 플러그인이 아니다.

앱 기획, 기술 결정, 구현, 품질 관리, 사용자 가치 검증, 의존성 관리, 라이선스 관리, 실행 검증을 하나의 반복 가능한 생산 공정으로 만드는 시스템이다.

핵심 경쟁력은 다음과 같다.

빈 폴더에서 시작할 수 있다.

사용자의 판단이 필요한 항목을 빠짐없이 질문한다.

모르는 값은 임의 생성하지 않고 Placeholder로 관리한다.

최신 안정화 라이브러리를 공식 문서에서 확인한다.

라이선스가 불명확하거나 상업용 앱과 충돌할 가능성이 있는 의존성을 자동 차단한다.

구현 Agent와 검증 Agent를 분리한다.

부분 구현을 완료로 인정하지 않는다.

Claude Code와 Codex를 모두 지원한다.

두 Provider를 교차 검증에 활용할 수 있다.

중단 후 작업을 이어갈 수 있다.

반복되는 앱 개발 공정을 자동화할 수 있다.

최종적으로 App Factory Autopilot은 factory plan, factory go, factory review 세 명령만으로 앱 기획부터 최종 정밀검증까지 수행하는 범용 앱 개발 자동화 플러그인을 목표로 한다.
